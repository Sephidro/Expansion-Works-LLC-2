HighLevel Finally Added Jotform. Keep It Away From Payment Forms for Now.

The triggers can remove a Zapier step. The Create Submission action can also make an unpaid record look paid.

By Xavier Pearson · Updated September 23, 2026 · Facts checked September 23, 2026 · 5 min read

HighLevel finally put Jotform inside its workflow builder. I immediately wanted to delete a Zap.

Then I hit one sentence in the release notes that stopped me: on a payment form, HighLevel’s Create Submission action can make an unpaid record look identical to a paid one.

That gives me two verdicts, not one. Test the incoming triggers beside your current handoff. Keep Create Submission away from payment forms until nobody can mistake a workflow-created submission for money collected.

The shortcut I actually want

The useful part is not “more integrations.” It is getting rid of a handoff no one owns.

A Jotform inquiry can create or update the contact, trigger the acknowledgment, add the right tag, and put the next action in front of a person. A signed document can move the opportunity and create onboarding work without someone watching an inbox.

That is the exact kind of boring automation I like. The customer does one thing, the system records it once, and the next person knows what to do.

HighLevel says new submissions trigger immediately. Signed documents are checked every five minutes. The connection uses a Jotform API key, then loads the chosen form fields for mapping.

Here is the trap

HighLevel also published a limitation big enough to change the recommendation.

Its Create Submission action does not support file uploads, signatures, appointments, payments, product lists, terms and conditions, and several other field types. Those fields do not appear in the mapper. If an unsupported field is required, HighLevel says Jotform can still accept the submission, leave the field empty, and mark the record active.

The payment behavior is worse. A workflow-created submission on a payment form carries no payment, amount, product, or booked time. HighLevel says it can look identical to a paid submission.

That is not a small edge case. A clean-looking record with no money behind it is how an automation upgrades from “convenient” to “who told the client they were paid?”

Make it earn the delete button

I would build the native connection beside the current handoff and try to make the records misleading on purpose:

  • Submit a normal lead and trace every mapped field into HighLevel.
  • Sign a dummy agreement and confirm onboarding starts once.
  • Make an unsupported field required and see whether Jotform still marks the incomplete record active.
  • Create a submission on a payment form without paying. Then hand the record to someone who did not build the workflow and ask what they think happened.

Trace both systems. Check the Jotform record, HighLevel contact, opportunity stage, tags, messages, duplicates, and activity history. Disconnect the API key. Confirm what breaks, where the failure is logged, and how the workflow recovers.

The native integration wins only when the records stay unambiguous and a failure is easier to spot than the one in the current Zapier or webhook setup. If it passes, delete a moving part. If it does not, keep the boring connection that already works.

What I have not tested

I have used HighLevel, but I have not run this Jotform release. The supported fields, timing, empty required fields, and payment-record behavior above come from HighLevel’s own release notes. The release does not name a separate integration price, and I did not find a documented export for mappings or run history.

That uncertainty does not make the feature useless. It makes this a source-backed test plan, not a recommendation to move production data today.

The no-buy path is five minutes of manual work

If you receive a few forms each month, keep the current manual handoff. Copy the useful fields, create the next action, and move on. A new connection is not automatically simpler just because the menu finally contains both logos.

If you already use both platforms and a third-party handoff is costing money or failing, test the native route. Keep payment truth in the payment system. Keep signatures attached to the human action that created them. Let this integration handle ordinary lead data first.

If the bigger problem is that leads enter three systems and nobody can tell which one owns the next action, [Build a StackBrief](/stackbrief) before replacing one connector with another.
